# Runtime conformance and compatibility v1

This repository's conformance suite is fixture-driven and runs with Node.js 22, ES modules and ES2022 language/library features. The root runtime is headless and has no implicit browser, clock, random, UI framework, XState, network or storage dependency. `./loading` is the optional Node loading adapter; `./effects` and `./persistence` are separate opt-in coordinators; `./schemas/effect-request.v1.schema.json` is the exported effects schema. The package export map is the public boundary. Internal scripts, tests and implementation files are not package entry points.

The `npm test` suite covers the Protocol EngineSession methods (`dispatch`, `evaluate`, `serialize`, `restore`, `dispose`), Core lifecycle controls, state/event subscriptions, cleanup and failure boundaries. The end-to-end fixture registers the real Quiz engine and a renderer under Registry, creates its GenerationCatalog, validates an AI-generatable learner activity through Protocol and Quiz's trusted validator, loads it through Core, answers and evaluates it, validates Events, serializes a Protocol snapshot and restores that snapshot into a fresh engine. Quiz's catalog schema references Content Node by URL; Registry's generic schema helper correctly rejects that external reference instead of fetching it, so this slice uses Quiz's bundled validator and does not claim generic cross-repository schema bundling. Invalid domain data and a catalog that denies `aiGeneratable` must stop before the engine factory is called. Existing focused fixtures cover cancellation, timeouts, permission/capability gates, malformed and duplicate-key JSON, stale actions, pending/failed outcomes, corrupt snapshots, cleanup, effects and persistence.

The renderer fixture selects Registry's `dom` host and receives only a tiny `{textContent}` mount port. This proves host selection, renderer lifecycle and Core's framework-neutral boundary in a Node process with no `window` or `document`; it does not claim browser DOM behavior or replace a production renderer. The `interactive-project/renderer-dom` repository currently has no implementation to import. Browser layout, accessibility, event handling and rendering remain unsupported until that package supplies its own host conformance suite. React, Vue, Svelte and XState are not Core dependencies or peers. The existing state-machine facade verifies the portable adapter seam, not a particular XState release.

## Dependency and release policy

Core's peer dependencies are Protocol, Events and Registry at the matching `0.1.0` contract version. Ajv and ajv-formats are optional peers for Node schema-validation consumers, not requirements of the headless root runtime. Quiz and Content Node are dev-only dependencies used by the real integration fixture; they are not required to consume Core. CI pins every Git dependency to a reviewed commit SHA and runs `npm ci --ignore-scripts` followed by the full suite on Node.js 22. Those repository coordinates do not assert that any `@interactive-project/*` package has been published to npm.

Protocol wire schemas remain versioned independently from package versions. A dependency release that keeps its declared contract version must pass the pinned conformance suite before Core updates its SHA. A Protocol, Events or Registry contract-version change requires an explicit compatibility review and coordinated fixtures; do not silently widen a peer range. Before claiming compatibility with a new independently released Quiz, renderer or optional XState adapter, run the same contract suite against that exact release/commit in a separate CI job and retain the pinned job as the reproducible baseline. Optional adapters must remain separately installable and may not leak vendor objects into public JSON or snapshots.

## Known limits and migration

The current vertical slice covers Quiz v1 and Protocol/Events/Registry contract v1 only. It does not certify a browser renderer, XState package integration, remote effects, crash-durable event delivery, or cross-major snapshot migration. Core's own snapshots remain bound to their declared schema and engine versions; hosts must reject unsupported versions or perform an explicit validated migration before restore. No shared wire contract or existing serialized format changed for this conformance work.
